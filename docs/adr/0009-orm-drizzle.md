# 9 · The ORM is Drizzle with SQL migrations; Prisma is removed

- Status: accepted
- Date: 2026-10-28

## Context

The data layer is rewritten anyway to add `tenant_id`, RLS and a tenant-scoped client. Prisma 5.19 is two majors behind (7 is stable, 8 is in release-candidate and replaces client extensions, which an RLS wrapper would depend on). The owner chose Drizzle (decision D2, 2026-10-28). bd-pos uses Drizzle 0.45 with postgres-js.

## Decision

Use `drizzle-orm` and `drizzle-kit` with the `postgres` (postgres-js) driver. The schema starts as an exact port (parity) of the current Prisma schema: same table, column and enum names, so an existing database needs no data move, only a baseline marker (plan 03). `tenant_id` and RLS are added in Phase 1 (plan 04), when the schema file is split into `packages/db/src/schema/*.ts`. Migrations are SQL files generated by drizzle-kit and committed; RLS statements are hand-written SQL migrations. `packages/db` exports `db`, and from Phase 1 `withTenant`, `asSystem`, `tenantScopedTables` and `platformTables`. RLS is applied as `set_config` inside a transaction, which Drizzle runs with `tx.execute(sql...)`. Repositories are the only code that imports table definitions. Pin exact versions because Drizzle 1.0 is still in beta.

## Consequences

- No Prisma client generation step and no Rust engine in images. Smaller, faster Docker builds.
- SQL stays visible; RLS and pgvector fit naturally.
- We lose Prisma Studio. Use Drizzle Studio or psql.
- Relations are defined by hand and queries are typed but lower level, so repositories carry more code.
- Seed and the TMDB import script must be rewritten.
- `bigint`, `Json` and enum mappings need explicit tests (the old `VideoFile.size` is a BigInt).

## Alternatives considered

- Prisma 7: current stable, but its client-extension RLS pattern breaks again with Prisma 8.
- Prisma 8: not GA as of 2026-10-28 (unverified).
- Kysely or raw SQL: more control, no schema-as-code.
